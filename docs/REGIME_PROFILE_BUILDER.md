# Regime Profile Builder

Внутренний полуавтоматический конвейер для переноса профиля из векторной режимной карты PDF в отдельный JSON участка.

Builder не является пользовательской функцией приложения. Команды `inspect`, `build`, `apply-review` и `check` работают только с артефактами запуска вне `assets/tracker/sections`. Изменить продуктовый JSON может только отдельная команда `promote`: она допускает строгое in-place обновление одного выбранного файла участка после полностью закрытой ручной проверки и синхронизирует его `profile_status` в `index.json`.

## Рабочий процесс

1. Скопировать `tools/regime_profile_builder/config.example.json` в `tmp/pdfs/regime-profile-builder/configs/<section>.json`.
2. Указать PDF, диапазон участка и при наличии существующий JSON только как `compare_seed`.
   Если конкретная страница экспортирована со стабильным сдвигом пикетной фазы, его можно явно зафиксировать в `page_coordinate_offsets_m`, например `{"11": 100}`. Значение обязано быть кратно `snap_m`, сохраняется в evidence/diagnostics и не применяется неявно к другим страницам.
   Для страниц с двумя независимыми шкалами используются явные `page_windows` с собственным `axis_override` и `keep_m`. Перекрытия разных страниц разрешаются только через `page_priorities`: побеждает единственный источник с большим приоритетом, равенство и конфликт внутри одной страницы остаются блокировкой.
   Реальный разрыв километража или недорисованный край карты можно объявить в `allowed_profile_gaps` с обязательной причиной. Builder принимает только точно наблюдаемый разрыв; если элементы внезапно перекрыли объявленный gap или его границы изменились, проверка блокируется.
3. Проверить распознанные страницы и тип бланка:

```powershell
npm run regime:profile -- inspect --config <config.json> --out <run-dir>
```

4. Построить черновой профиль, отчёт и изображения спорных ячеек:

```powershell
npm run regime:profile -- build --config <config.json> --out <run-dir>
```

5. Открыть `<run-dir>/review/contact-sheet.png` и `<run-dir>/review.json`. Проверять нужно только перечисленные конфликты, а не все страницы PDF.
6. Заполнить решения на основе `decisions.example.json` и применить их к артефакту запуска:

```powershell
npm run regime:profile -- apply-review --run <run-dir> --decisions <decisions.json>
```

Для большой карты решения можно разделить по страницам и передать несколькими повторяющимися аргументами `--decisions`; builder объединит их в памяти, проверит общий SHA PDF и запретит повтор одного `issue_id` в разных фрагментах.

Для обычной ячейки решение использует `accept_suggestion`, `keep_seed`, `set_grade`, `accept_geometry` или `defer`. Если величина вручную перенесена из согласованного legacy-профиля, применяется отдельное действие `set_grade_from_legacy`: оно сохраняет `manual_reviewed_legacy_fallback`, а не маскирует источник под PDF. Для настоящего разрыва без готовой строки используется `insert_gap` с обязательным `grade_permille`; поэтому редкий пропуск можно исправить в файле решений, не меняя код адаптера.

После `apply-review` появляется `<run-dir>/reviewed.profile.json`. Повторять ручную проверку и применение решений нужно до нулевой очереди, затем обязательно выполнить строгую проверку:

```powershell
npm run regime:profile -- check --run <run-dir> --require-clean
```

`check` автоматически проверяет `reviewed.profile.json`, если он существует; иначе проверяет `draft.profile.json`. Флаг `--require-clean` завершает команду ошибкой, пока остался хотя бы один нерешённый вопрос.

7. Только после успешного `check --require-clean` перенести проверенный профиль в продуктовый JSON участка:

```powershell
npm run regime:profile -- promote `
  --run <run-dir> `
  --section assets/tracker/sections/<section>.json `
  --out assets/tracker/sections/<section>.json
```

`promote` намеренно не умеет писать в новый файл: `--section` и `--out` должны указывать на один и тот же верхнеуровневый JSON внутри `assets/tracker/sections`. Перед записью команда проверяет наличие `reviewed.profile.json`, полное соответствие решений исходной очереди, SHA-256 PDF, значений профиля и уровней confidence, границы участка и непрерывность покрытия за вычетом только точно наблюдаемых `allowed_profile_gaps`. Она заменяет профиль, обновляет его provenance/runtime и зеркальный `profile_status` каталога, но сохраняет остальные данные участка, включая станции, GPS-геометрию и общий `status`.

8. Проверить продуктовые файлы:

```powershell
npm run sections:validate
npm run sections:test
```

## Поддерживаемые бланки

- `blue_bottom_table`: нижняя таблица уклонов и синяя векторная трасса, как на карте Постышево - Комсомольск-Сортировочный. Обычные слова имеют приоритет, а повёрнутые подписи восстанавливаются из последовательных PDF chars; фактическая нижняя граница таблицы отсекает числа из служебной строки под ней. Если CAD-экспорт потерял только внешнюю вертикаль крайней ячейки, адаптер восстанавливает её по концу синей трассы лишь при одновременном совпадении PDF-величины, напечатанной длины и метрического масштаба оси.
- `black_grade_strokes`: компактные чёрные диагонали таблицы задают первичный знак уклона, как на карте Постышево - Новый Ургал; толстая верхняя трасса используется только для QA. Знак нормализуется по направлению километровой оси, поэтому формат работает и при возрастающей, и при убывающей шкале.
- `diagonal_grade_table`: нижняя таблица, где знак уклона задан диагональю (`/` подъём, `\\` спуск), как на карте Волочаевка II - Дзёмги. Адаптер восстанавливает границы по векторной рамке и 100-метровой пикетной шкале, читает обычные и повёрнутые подписи величин, сверяет напечатанные длины и использует синюю трассу как дополнительную проверку. Противоречие источников или отсутствующая величина отправляются в ручную очередь.
- `auto`: выбирает адаптер отдельно для каждой страницы только при однозначном результате.

Сканированные PDF без векторных линий пока блокируются. Builder не подменяет такой документ догадками или молчаливым чтением одного текстового слоя.

## Артефакты запуска

- `run.json`: версия builder, fingerprint PDF и итоговые числа;
- `pages.json`: найденные оси, адаптеры и диагностика страниц;
- `cells.json`: доказательства по каждой логической ячейке;
- `draft.profile.json`: черновой профиль без GPS, станций и продуктового статуса;
- `review.json`: только спорные места со стабильными `issue_id`;
- `review/*.png` и `review/contact-sheet.png`: крупные фрагменты PDF;
- `decisions.example.json`: шаблон ручных решений;
- `reviewed.profile.json`: результат `apply-review` с перечнем закрытых/оставшихся вопросов и контрольным SHA-256 элементов;
- `summary.md`: краткий итог запуска.

Абсолютные пути к локальным вложениям не записываются в артефакты. Повторная запись существующего запуска требует явного `--force`.

## Политика достоверности

Автораспознавание и `apply-review` никогда не выдают продуктовый `verified`: `reviewed.profile.json` остаётся проверенным черновым артефактом. Только явный `promote` после чистой проверки выставляет `runtime.profile_status: "pdf_verified"`. Если в решениях есть `set_grade_from_legacy`, статус честно принимает вид `pdf_profile_audited_<N>_legacy_magnitudes`. Общий `status` участка в обоих случаях не повышается автоматически, потому что GPS, станции и остальные данные имеют собственный цикл проверки.

- `pdf_vector_confirmed`: ось, границы, напечатанная величина и основной векторный знак конкретного формата согласованы;
- `pdf_manual_evidence_replayed`: повторно применено уже сохранённое ручное PDF-решение;
- `needs_review`: отсутствует подпись, слабый знак, используется legacy-подсказка или источники противоречат друг другу;
- `blocked`: не найдены обязательные части бланка либо профиль имеет разрыв/пересечение.

Legacy JSON используется только как предложение. Непроверенное значение из него не может автоматически стать подтверждённым.

Для миграции уже существующего XML/legacy-профиля можно явно включить `"reconcile_seed_order": true` вместе с `compare_seed`. Тогда builder сопоставляет последовательности ячеек по напечатанной величине, векторному знаку и длине, а границы черновика выравнивает по legacy-последовательности. Режим не скрывает расхождения: seed-only элементы, лишние PDF-ячейки и значения без PDF-доказательства остаются `needs_review`. По умолчанию эта возможность выключена.

Если между двумя извлечёнными границами отсутствует ровно один ранее вручную проверенный элемент, builder может вставить его только как `needs_review` с причиной `missing_pdf_cell_manual_seed_suggestion`. Такая строка остаётся отдельной, не сливается с соседними элементами и обязательно попадает в очередь проверки. Непроверенный legacy-элемент разрыв заполнить не может.

## Acceptance на реальных картах

- Оунэ - Пивань: 15 профильных страниц сведены в 341 элемент на диапазоне 1 000..184 000 м. Явными смещениями пикетной фазы исправлены страницы 13, 15, 17, 19, 25 и 33; крайняя ячейка страницы 19 восстановлена по синей трассе и подписи `3,8‰ / 400 м`. Перекрывающиеся части `−2,15‰ / 1200 м` на страницах 23/25 и `+3,7‰ / 300 м` на страницах 25/27 состыкованы без искусственных вставок, а одинаковые уклоны на трёх стыках страниц канонически объединены. Страница 31 доказательно исключена как соседний чётный путь. Получено 122 прямых векторных подтверждения, 128 повторно применённых ручных PDF-доказательств и 91 решение текущей проверки. Две узкие 100-метровые ячейки без печатной подписи на 168,5 и 170,5 км восстановлены по масштабу синей трассы как `−1,7‰` и `+2,5‰`; масштаб сверён с соседними подписанными уклонами, поэтому legacy fallback в профиле больше нет. Реальный скачок километража 94,0→91,3 км остаётся явным gap 91 300..94 000 м с причиной.
- Пивань - Новый Мир: раздельная шкала после станции Пивань на странице 41 отделена `axis_override`, страница 43 пристыкована без ложных пересечений. Получено 32 элемента на покрытии 1 300..17 000 м: 21 подтверждён автоматически, 11 повернутых/краевых ячеек проверены по PDF, legacy fallback нет. Недорисованный исходной картой край 1 000..1 300 м сохранён как явный gap с причиной, а не заполнен догадкой.
- Высокогорная - Оунэ через Соллу: страницы 5, 7 и 9 дали непрерывный диапазон 183 000..220 900 м из 33 элементов. 32 элемента подтверждены автоматически, краевой интервал 183 000..183 200 м с `+2,4‰` вручную подтверждён перекрывающей страницей 13; legacy fallback нет.
- Высокогорная - Оунэ через Мули: страницы 11 и 13 дали непрерывный диапазон 183 000..210 000 м из 36 элементов. Восстановлены наложенные CAD-подписи километровой оси `208..196`, явно учтён сдвиг обеих страниц `+100 м`; 25 элементов подтверждены автоматически, 11 повернутых/конфликтных ячеек проверены непосредственно по PDF, legacy fallback нет.
- Постышево - Комсомольск-Сортировочный: 362 исходные ячейки и 358 логических элементов. После 8 ручных решений числовой профиль остался идентичен ранее проверенному JSON: 350 элементов повторно подтверждены PDF-доказательством, 2 конфликта печатной длины закрыты по пикетной сетке, 6 нечитаемых величин явно помечены как legacy fallback; нерешённых вопросов нет.
- Постышево - Новый Ургал: 32 страницы и 897 исходных ячеек. После перехода на знак компактной диагонали получено 879 логических элементов: 872 подтверждены автоматически, 7 проверены вручную, блокировок и нерешённых вопросов нет. Исправлены 12 интервалов с ошибочным знаком старого профиля; 100-метровая ячейка 3418,9–3419,0 км подтверждена непосредственно по PDF без legacy fallback.
- Волочаевка II - Дзёмги: страницы 2-26; специализированный диагональный адаптер без автоматического наследования legacy-профиля построил черновик из 481 элемента, 458 из них подтвердил векторами PDF. После 26 ручных решений, включая заполнение начального разрыва 9 000..9 300 м, получен непрерывный `reviewed.profile.json` из 482 элементов на диапазоне 9 000..361 000 м; `check --require-clean` показывает 0 нерешённых вопросов. У 10 плохо читаемых величин явно сохранён источник `manual_reviewed_legacy_fallback`: их границы, длины и знаки согласованы с PDF, а численное значение перенесено из legacy-профиля.

Эти числа являются локальным acceptance известных профилей и форматов, а не обещанием распознавания любого произвольного PDF. Новый тип бланка добавляется отдельным адаптером и проверяется на эталонной карте.

## Проверки

```powershell
npm run regime:builder:test
npm run smoke:predeploy
```

Unit-тесты не зависят от локальных путей `codex-remote-attachments`. Реальные PDF используются для отдельного локального acceptance и визуальной проверки contact sheet.
