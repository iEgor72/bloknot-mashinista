# Regime Profile Builder

Внутренний полуавтоматический конвейер для переноса профиля из векторной режимной карты PDF в отдельный JSON участка.

Builder не является пользовательской функцией приложения. Он создаёт только черновик и пакет ручной проверки. Файлы `assets/tracker/sections/*.json` и `index.json` он не изменяет.

## Рабочий процесс

1. Скопировать `tools/regime_profile_builder/config.example.json` в `tmp/pdfs/regime-profile-builder/configs/<section>.json`.
2. Указать PDF, диапазон участка и при наличии существующий JSON только как `compare_seed`.
3. Проверить распознанные страницы и тип бланка:

```powershell
npm run regime:profile -- inspect --config <config.json> --out <run-dir>
```

4. Построить черновой профиль, отчёт и изображения спорных ячеек:

```powershell
npm run regime:profile -- build --config <config.json> --out <run-dir>
```

5. Открыть `<run-dir>/review/contact-sheet.png` и `<run-dir>/review.json`. Проверять нужно только перечисленные конфликты, а не все страницы PDF.
6. Заполнить решения на основе `decisions.example.json` и применить их только к артефакту запуска:

```powershell
npm run regime:profile -- apply-review --run <run-dir> --decisions <decisions.json>
npm run regime:profile -- check --run <run-dir>
```

Для обычной ячейки решение использует `accept_suggestion`, `keep_seed`, `set_grade`, `accept_geometry` или `defer`. Для настоящего разрыва без готовой строки используется `insert_gap` с обязательным `grade_permille`; поэтому редкий пропуск можно исправить в файле решений, не меняя код адаптера.

Перенос `reviewed.profile.json` в продуктовый section JSON остаётся отдельным осознанным действием после ручной проверки.

## Поддерживаемые бланки

- `blue_bottom_table`: нижняя таблица уклонов и синяя векторная трасса, как на карте Постышево - Комсомольск-Сортировочный.
- `black_grade_strokes`: компактные ячейки уклонов и чёрная векторная трасса, как на карте Постышево - Новый Ургал.
- `auto`: выбирает адаптер отдельно для каждой страницы только при однозначном результате.

Сканированные PDF без векторных линий пока блокируются. Builder не подменяет такой документ догадками или молчаливым чтением одного текстового слоя.

## Артефакты запуска

- `run.json`: версия builder, fingerprint PDF и итоговые числа;
- `pages.json`: найденные оси, адаптеры и диагностика страниц;
- `cells.json`: доказательства по каждой логической ячейке;
- `draft.profile.json`: черновой профиль без GPS, станций и продуктового статуса;
- `review.json`: только спорные места со стабильными `issue_id`;
- `review/*.png` и `review/contact-sheet.png`: крупные фрагменты PDF;
- `decisions.example.json`: шаблон ручных решений;
- `summary.md`: краткий итог запуска.

Абсолютные пути к локальным вложениям не записываются в артефакты. Повторная запись существующего запуска требует явного `--force`.

## Политика достоверности

Builder никогда не выдаёт продуктовый `verified`.

- `pdf_vector_confirmed`: ось, границы, напечатанная величина и знак трассы согласованы;
- `pdf_manual_evidence_replayed`: повторно применено уже сохранённое ручное PDF-решение;
- `needs_review`: отсутствует подпись, слабый знак, используется legacy-подсказка или источники противоречат друг другу;
- `blocked`: не найдены обязательные части бланка либо профиль имеет разрыв/пересечение.

Legacy JSON используется только как предложение. Непроверенное значение из него не может автоматически стать подтверждённым.

Если между двумя извлечёнными границами отсутствует ровно один ранее вручную проверенный элемент, builder может вставить его только как `needs_review` с причиной `missing_pdf_cell_manual_seed_suggestion`. Такая строка остаётся отдельной, не сливается с соседними элементами и обязательно попадает в очередь проверки. Непроверенный legacy-элемент разрыв заполнить не может.

## Acceptance на реальных картах

- Постышево - Комсомольск-Сортировочный: 362 исходные ячейки, 358 логических элементов, точное совпадение всех границ и уклонов с ранее вручную проверенным JSON; ручная очередь сокращена до 8 ячеек.
- Постышево - Новый Ургал: 32 страницы, 897 извлечённых ячеек; после объединения продолжений на границах страниц получено 880 логических элементов, из них 865 подтверждены векторами PDF и 15 оставлены на ручную проверку. Блокирующих разрывов нет; один отсутствующий 100-метровый элемент сохранён как отдельная ручная подсказка.

Эти числа являются локальным acceptance двух известных форматов, а не обещанием распознавания любого произвольного PDF. Новый тип бланка добавляется отдельным адаптером и проверяется на эталонной карте.

## Проверки

```powershell
npm run regime:builder:test
npm run smoke:predeploy
```

Unit-тесты не зависят от локальных путей `codex-remote-attachments`. Реальные PDF используются для отдельного локального acceptance и визуальной проверки contact sheet.
