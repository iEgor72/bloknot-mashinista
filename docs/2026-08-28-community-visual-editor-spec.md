# Визуальный редактор участка — UX-контракт

## Цель первого рабочего этапа

Машинист без технической подготовки должен уметь открыть реальный профиль своего
участка, выбрать пальцем точные границы изменения, увидеть предварительный результат
и отправить коллегам структурированную правку профиля или скорости.

## Основной сценарий

1. Пользователь открывает `Профиль → Моё депо → Визуальный редактор`.
2. Выбирает участок из пакета своего депо.
3. Ползунком перемещает окно вдоль километровой оси.
4. Перетаскивает две границы выделения непосредственно на профиле.
5. Выбирает режим `Уклон`, `Скорость` или `Объекты` и задаёт изменение крупными органами управления.
6. Редактор показывает границы в формате `км + пикет`, длину и визуальный предпросмотр.
7. Для повышения скорости пользователь обязан указать приказ или другой источник.
8. На сервер уходит не свободный текст, а диапазон `startM/endM`, исходное и новое значение,
   идентификатор участка и версия исходного файла.

## Ограничения безопасности

- Границы привязываются к шагу 100 метров и не могут выходить за участок.
- Минимальная длина изменения — 100 метров.
- Максимальная длина одной правки — 20 километров: более крупные изменения разбиваются.
- Исходный JSON не изменяется на телефоне и сервере; создаётся proposal.
- Повышение скорости и снятие ограничения без документального основания отклоняются API.
- GPS-высота не используется как автоматическая замена железнодорожного профиля.

## Формат change payload

```json
{
  "editor": "visual-v1",
  "sectionId": "dvost-postyshevo-komsomolsk",
  "startM": 3718200,
  "endM": 3719000,
  "source": {
    "schemaVersion": "1.0",
    "profileStatus": "pdf_profile_audited_6_legacy_magnitudes",
    "communityVersion": 3
  },
  "fromGrade": 1.0,
  "toGrade": 0.0
}
```

Для скорости используются `fromSpeed`, `toSpeed` и `action` (`set` или `remove`).

## Интерактивные объекты карты

В режиме `Объекты` пользователь касается профиля и выбирает понятный рабочий тип, не имя JSON-поля:

- станция или остановочный пункт;
- входной, выходной или проходной светофор;
- знак `С` и точка подачи свистка;
- `НТ`, `КТ`, `КТСМ`, нейтральная вставка;
- тяговая позиция, соединение схемы;
- пометка о торможении, количестве позиций или произвольная подпись под профилем.

Видимые объекты показываются на схеме и списком в текущем шестикилометровом окне. Объект можно выбрать касанием, изменить или предложить удаление. Клиент отправляет ссылку на исходный объект, но сервер повторно находит его в действующей версии участка и не доверяет переданному имени или координате.

Каждый тип имеет собственную масштабируемую SVG-иконку в визуальном стиле приложения. Один и тот же `kind` определяет знак в горизонтальном каталоге выбора, предпросмотре добавления, списке ближайших объектов и на canvas-профиле. Это не копия обозначений режимной карты: сохраняется рабочий смысл, но используются тёмные поверхности, голубой акцент приложения и смысловые цвета для начала/конца торможения, сигналов и инфраструктуры. При плотном расположении маркеры автоматически разводятся по трём ярусам и соединяются с точной координатой тонкой линией.

```json
{
  "editor": "visual-v1",
  "sectionId": "dvost-postyshevo-komsomolsk",
  "coordinateM": 3718200,
  "action": "add",
  "object": {
    "kind": "ktsm",
    "collection": "infrastructure",
    "name": "КТСМ 3718",
    "direction": "odd"
  }
}
```

Для `update` и `remove` добавляется `sourceObject` с устойчивым `objectKey`; коллекция и индекс остаются вспомогательными полями для старых исходных объектов. Удаление или перенос станции, сигнала, знака безопасности, НТ/КТ/КТСМ требует документального источника и получает уровень `safety_increase`. Добавление предписывающего знака `С`, точки свистка или `НТ` получает `safety_restriction`; остальные новые объекты проходят обычный кворум.

## Решение о версиях участка

Принята модель неизменяемого исходника и последовательного журнала опубликованных правок.

- JSON участка в репозитории остаётся исходной картой и никогда не перезаписывается голосованием.
- Каждая принятая правка становится отдельным release с монотонным номером версии в рамках участка.
- API `GET /api/community/sections/:sectionId/effective` собирает актуальный участок при чтении: клонирует исходник и по порядку применяет опубликованные правки профиля и объектов.
- Скорости хранятся отдельным упорядоченным слоем диапазонов, потому что исходная схема скоростей ещё не содержит полного набора рабочих ограничений.
- Ответ содержит номер версии, историю применённых release и список пропущенных конфликтных release.
- Редактор передаёт `communityVersion`. Если за время редактирования коллеги уже опубликовали следующую версию, сервер отклоняет устаревшую отправку и просит загрузить участок заново.
- У каждого добавленного или изменённого элемента сохраняются `community_release_id`, `community_proposal_id` и номер версии для разбора происхождения.

Такой слой выбран вместо генерации нового JSON после каждого голосования: журнал не теряет историю, исходную карту можно воспроизвести, а будущий откат оформляется новой проверяемой правкой, а не удалением данных.

В раскрываемой истории активная версия имеет действие `Отменить`. Машинист указывает понятную причину и, если отмена может снять ограничение, приказ или другое основание. Создаётся обычное предложение для коллег:

```json
{
  "editor": "rollback-v1",
  "action": "rollback",
  "sectionId": "dvost-postyshevo-komsomolsk",
  "targetReleaseId": "release:...",
  "source": { "communityVersion": 5 }
}
```

После публикации целевая версия помечается в истории как отменённая, но не удаляется из базы. Повторная отмена той же версии и отправка поверх устаревшей `communityVersion` отклоняются.

## Редактор GPS-геометрии

GPS-геометрия редактируется в отдельном картографическом режиме и не смешивается с уклоном:
километровая ось, высотный профиль и географические координаты остаются разными слоями данных.

1. Пользователь выбирает участок и одну из поездок, ранее записанных с GPS в режиме `Поехали`.
2. Редактор сопоставляет `nearestPathId` и координату записи с опубликованным `geometry.paths[].path_id`.
3. На схеме одновременно показаны опубликованная линия, исходная GPS-запись и предлагаемый фрагмент.
4. Место наибольшего расхождения находится автоматически; границы можно поправить двумя крупными ползунками.
5. Предлагаемые контрольные точки можно перетаскивать пальцем и удалять по одной, если телефон дал ошибочную точку.
6. Полный локальный трек не отправляется. В proposal попадают только прореженные точки выбранного фрагмента.

```json
{
  "editor": "visual-v1",
  "sectionId": "dvost-postyshevo-komsomolsk",
  "action": "replace_fragment",
  "pathId": "postyshevo-komsomolsk-sector-18",
  "startM": 3717100,
  "endM": 3718800,
  "points": [
    { "chainageM": 3717200, "lat": 51.2001234, "lon": 136.7001234, "accuracyM": 8 }
  ],
  "source": { "communityVersion": 4 }
}
```

Сервер повторно находит путь в актуальной версии, проверяет диапазон, шаг контрольных точек,
географические границы и максимальное удаление от опубликованной линии. Стыковые точки `startM/endM`
берутся из текущей линии автоматически, поэтому новый фрагмент не образует разрывов. В release сохраняются
происхождение и версия каждой опубликованной точки. Геометрия считается чувствительной правкой: требуется
основание в виде записанной поездки или другого источника и усиленный кворум.

## Использование в «Поехали»

Для маршрутов из JSON `Поехали` автоматически запрашивает effective section и применяет подтверждённые профиль, GPS-геометрию, станции, сигналы, скорости и отметки под профилем. Успешный ответ сохраняется для офлайн-работы. При ошибке API приложение использует совместимую сохранённую копию либо исходный JSON, поэтому отсутствие сети не блокирует режим поездки.
