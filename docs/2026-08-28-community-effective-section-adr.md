# ADR: Актуальная версия участка как наложение опубликованных правок

**Статус:** реализовано для визуального редактора и рабочего режима «Поехали»
**Дата:** 28.08.2026
**Решение:** владелец приложения; публикацию выполняет сообщество по действующим правилам проверки

## Контекст

Исходные участки поставляются как JSON, но профиль, скорости и объекты меняются быстрее, чем один администратор способен обновлять всю сеть. Пользовательские изменения должны становиться видны коллегам после проверки, при этом ошибка сообщества не должна уничтожать исходные данные или историю.

## Решение

Хранить исходный JSON неизменяемым, а каждое принятое предложение — как неизменяемый release с номером версии внутри участка. Сервер при чтении строит effective section: клонирует исходник и последовательно применяет опубликованные release.

Профиль, объекты и проверенные фрагменты GPS-геометрии накладываются на копию участка. Скорости пока возвращаются отдельным упорядоченным слоем диапазонов. Каждый изменённый элемент получает происхождение (release, proposal, version), а каждый объект — устойчивый `objectKey`.

Редактор загружает только effective section и отправляет увиденную `communityVersion`. Сервер отклоняет запись поверх устаревшей версии.

Отмена ошибочной публикации оформляется новым proposal типа `section` с `editor: rollback-v1` и ссылкой `targetReleaseId`. После обычной проверки новый release не удаляет старую запись, а заставляет resolver пересобрать участок без отменённой версии. В истории остаются и исходная правка, и решение об её отмене.

«Поехали» для JSON-участков сначала загружает штатный локальный файл, затем пытается получить effective section для пользователя его депо. Успешная проверенная версия сохраняется в отдельном Cache Storage. При отсутствии сети, авторизации или совместимого ответа используется последняя совместимая сохранённая версия, а если её нет — исходный JSON приложения.

## Рассмотренные варианты

| Вариант | Сложность | Восстановление | История | Выбран |
|---|---:|---:|---:|---:|
| Перезаписывать JSON после голосования | низкая сначала | сложное | теряется без Git | нет |
| Хранить одну изменяемую копию в БД | средняя | требует снимков | отдельный аудит | нет |
| Исходник + журнал release | средняя | воспроизведение по версиям | встроена | да |

## Последствия

- Исходная карта всегда доступна как точка восстановления.
- Можно показать точную историю и оформить отмену новым release.
- Конфликтный release не ломает весь участок: он попадает в `skipped` для разбора.
- Сборка участка линейна по числу release; при больших объёмах понадобятся периодические проверенные снимки.
- Рабочий режим «Поехали» использует effective section для профиля, GPS-линии, станций, сигналов, скоростей и служебных отметок.
- Опубликованные общие скорости имеют приоритет над локальной установленной/постоянной скоростью, но не перекрывают временное пользовательское ограничение и действующее предупреждение.
- Несовместимый или недоступный ответ API не блокирует поездку: остаётся локальная проверенная копия либо исходный JSON.

## Следующие действия

1. Ввести серверные периодические снимки effective section без удаления журнала.
2. Добавить в служебную диагностику «Поехали» видимый источник участка: сеть, офлайн-копия или исходный JSON.
3. Накопить полевые проверки приоритетов скоростей, направления и GPS-привязки на разных депо.
