# ADR-002: Единый контур областей, предложений и выпусков сообщества

**Статус:** Принято для первого этапа
**Дата:** 2026-08-28
**Ответственный за продукт:** владелец «Блокнота машиниста»

## Контекст

Статический каталог уже отделяет дороги, депо, плечи и повторно используемые участки. Пользовательские документы и материалы принимаются в карантинную очередь, а локальные GPS-участки и правки «Поехали» не покидают устройство. Для масштабирования на сеть нужен общий, аудируемый слой совместной работы, который не делает одного администратора обязательным экспертом каждого участка.

## Решение

Добавить в существующую SQLite четыре нормализованных компонента:

1. `community_memberships` — принадлежность и роль пользователя в области.
2. `community_proposals` — неизменяемая по смыслу заявка на точечное изменение с текущим workflow-статусом.
3. `community_reviews` — один актуальный отзыв пользователя на предложение.
4. `community_releases` и `community_audit_log` — выпуски областей и append-only история действий.
5. `community_elections`, `community_candidates`, `community_ballots` — выбор и отзыв нескольких кураторов в пределах депо или плеча.

Статический каталог остаётся источником организационной структуры и готовых пакетов. Новые таблицы не копируют весь каталог: они ссылаются на стабильные `railway_id`, `depot_id`, `service_arm_id`, `section_id`.

Пользовательский dashboard строится как объединение:

- профиля и членства пользователя;
- статического каталога дороги/депо/пакета;
- применимых предложений и проверок из SQLite;
- существующей очереди загруженных материалов автора.

## Рассмотренные варианты

### A. Продолжать хранить всё одной JSON-очередью

| Параметр | Оценка |
|---|---|
| Сложность старта | Низкая |
| Конкурентные изменения | Плохая |
| Аудит и выборки | Плохие |
| Масштабирование по областям | Плохое |

Плюс — минимум кода. Минусы — перезапись общего документа, трудные индексы, конфликты и невозможность надёжно обеспечить один голос пользователя.

### B. Нормализованные таблицы в текущем SQLite

| Параметр | Оценка |
|---|---|
| Сложность старта | Средняя |
| Совместимость с runtime | Высокая |
| Транзакции и аудит | Высокие |
| Эксплуатационная стоимость | Низкая |

Выбранный вариант. Он использует существующие миграции, резервные копии и один Node-runtime, не вводя преждевременно новый сервис.

### C. Отдельный облачный сервис сообщества

| Параметр | Оценка |
|---|---|
| Потенциальное масштабирование | Высокое |
| Операционная сложность | Высокая |
| Риск рассинхронизации | Высокий |
| Необходимость сейчас | Низкая |

Отложено. Текущая нагрузка и команда не оправдывают второй runtime и распределённые транзакции.

## Ключевые правила

- Организационная область и физический участок не являются отношением один-к-одному: один section может входить в несколько depot pack.
- Самостоятельный выбор депо не даёт доверенного голоса.
- Кураторская роль может быть получена через выборы подтверждённых участников области; роль ограничена областью и сроком.
- Выборы не создают единоличного владельца данных: выбирается коллегия кураторов, а критические изменения всё равно требуют основания и кворума.
- Правка не перезаписывает опубликованную сущность; она создаёт proposal и последующую revision/release.
- Изменение скорости хранит период действия. Отмена означает окончание действия старого правила, а не удаление истории.
- GPS-геометрия, профиль, объекты и скорости являются разными слоями.
- Повышение скорости проверяется строже снижения и требует основания.
- Клиент скачивает атомарный опубликованный пакет; предыдущий выпуск сохраняется для отката.

## Последствия

- Становятся возможны scoped dashboard, peer review, конфликты и автоматические выпуски.
- Появляется больше серверных сущностей и обязательных тестов прав доступа.
- До появления редактора часть предложений будет создаваться только через API или существующие формы загрузки.
- При росте нагрузки таблицы можно перенести в PostgreSQL, сохранив доменную модель и API.
